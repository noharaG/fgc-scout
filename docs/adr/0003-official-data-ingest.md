# 0003. 公式サイトの応答をサーバで代理取得し、生 JSON を原文のまま保つ

- ステータス: 採用
- 日付: 2026-09-10
- 関連: [0001](0001-cloudflare-and-origin.md)（代理取得がこの基盤を要求した）
- 関連: [0004](0004-contribution-estimation.md)（この取り込みが推定の唯一の入力）

## 背景

`https://results.first.global/` を実測して、次の4点を確認した。

1. Next.js の SSG で、`__NEXT_DATA__` に
   `props.pageProps.data = { matches, rankings, round_robin, finals,
alliances_round_robin, alliances_finals, awards }` が入る
2. `_next/data/<buildId>/index.json` からも同じ内容が取れる。
   HTML は 69KB、こちらは数百バイト
3. **CORS ヘッダが無い。**ブラウザから直接 fetch できない
4. `Cache-Control: s-maxage=10` で、元データ自体が10秒粒度

2026-09-10 時点では全配列が空である（大会前）。
したがって `matches[].details` に何が入るかは確認できていない。
去年のスクレイピングでは `details.redRobotOneParking` の形だったが、
今年はランキング列に `Climb Points` があり、名前が変わっている可能性が高い。

## 決定

サーバ側（`apps/api`）で代理取得し、次の形で扱う。

- 取得は `_next/data/<buildId>/index.json` を優先し、`buildId` が変わったら
  HTML の `__NEXT_DATA__` から取り直す二段構え
- 取得間隔は30秒以上。画面を開いた時のオンデマンドで、定期実行は持たない
- **取得した JSON を加工せずに原文のまま保存する。**解釈は読み出し側に置く
- 取得に失敗したら最後に成功した内容を返し、その取得時刻を必ず添えて表示する
- 知らないキーが来ても無視して描画を続ける

## 理由

原文のまま保つのは、`details` の形が大会が始まるまで分からないからである。
取り込み時に解釈して整形した形で保存すると、
形が判明した後に遡って解釈をやり直せない。
大会は数日で終わるので、やり直せないことは「その大会ぶんのデータを失う」に
直結する。

30秒以上にするのは、元データが `s-maxage=10` で10秒粒度しか持たないため、
それより細かく叩いても新しい値が返らないからである。
加えて、相手のサーバへ不要な負荷をかけない。

定期実行を持たないのは、部品を1つ減らせるうえ、
誰も画面を開いていない時間に相手のサーバを叩かずに済むためである。

## 検討

| 選択肢                                     | 却下の理由                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| ブラウザから直接 fetch する                | CORS ヘッダが無く、実測で不可能と確認した                                                                    |
| 取り込み時に正規化した形へ変換して保存する | `details` の形が未確認のまま変換規則を書くことになり、形が判明した後に遡れない                               |
| `_next/data` だけを使う                    | `buildId` は再ビルドで変わる。変わった時点で 404 になり、取り込みが止まる                                    |
| HTML の `__NEXT_DATA__` だけを使う         | 毎回 69KB を取得することになる。10秒粒度の相手に対して転送量が見合わない                                     |
| 定期実行で常時取り込む                     | オンデマンド取得と最終成功分の保持で足りる。誰も見ていない時間に叩かない                                     |
| 取得できないとき前回の値を黙って出す       | 古い値が最新に見える。何分前のものかを添えなければ、順位が動いていないのか取得が止まっているのか区別できない |

## 影響

`matches[].details` を読むコードは、大会開始まで書けない。
第1段では `matches` の `redScore` / `blueScore` / `participants` と
`rankings` だけで組み、`details` の対応は大会が始まってから足す。

この「知らないキーで落ちない」性質はテストで固定する。
`要件定義書.md` の7章の未決定1が解消した時点で、
マッピングを足すコミットでこの ADR に追記する。
