# 0004. チーム別の貢献を得点式と最小二乗の併用で推定する

- ステータス: 採用
- 日付: 2026-09-10
- 関連: [0003](0003-official-data-ingest.md)（推定の入力はここから来る）
- 関連: [0002](0002-package-layout.md)（計算をブラウザ内に置く判断）

## 背景

公式データはアライアンス単位の合計しか出さない。
作戦を立てるには「このチームが何点ぶん運ぶか」が要るが、
1試合に WILDFIRE が500個あり、1個1点なので、目視で数えることはできない。

当初は人力のマッチスカウトでサイクル数を実測し、
公開されている得点式（構造モデル）に代入する計画だった。
このとき統計的推定（FRC の OPR に相当する手法）は
「式が分かっているので不要」として却下していた。

2026-09-10 に方針が変わり、大会当日に試合中の記録へ人手を割けないことが
判明した。人力入力はピット訪問に集約し、試合中の記録は第3段へ降ろした。
**これにより「サイクル数を実測する」という前提が消え、
却下の根拠が失効した。**

## 決定

構造モデルと最小二乗を併用する。

得点式は次の形である（`要件定義書.md` の2.1）。

```text
MATCH SCORE = (SU点 × CLIMB乗数) + PARTNER CLIMB + EXTINGUISHER点
              + COOPERTITION BONUS
```

この式から3つの手がかりを使う。

1. **赤スコア − 青スコアでは Global 要素が消える。**
   EXTINGUISHER 点と COOPERTITION BONUS は両アライアンスに同じ値が入るため、
   差を取ると `(SU点 × 乗数) + PARTNER CLIMB` の差だけが残る
2. `rankings` の `Climb Points` が各チームのクライム実績を与える
3. `details` に各ロボットのクライム結果が入っていれば乗数が確定し、
   スコアから SU点 を分離できる（大会開始まで未確認）

毎試合アライアンスの組み合わせが変わるので、試合数がたまれば
チーム別の SU貢献を分離できる。

ピット記録の `capacity`（1回に運べる個数）は、
試合データが無い大会序盤の唯一の手がかりとして使う。

計算はブラウザ内で行う。

## 理由

得点式が公開されているので、純粋な統計的推定より構造を使ったほうが正確で、
かつ「なぜその予測になったか」を内訳として画面に出せる。
生徒に見せるものとして、説明できることの価値は大きい。

一方で、人力の実測が無い以上、SU点を チーム別に割り振る手段が
公式データの回帰以外に無い。よって併用になる。

ブラウザ内で計算するのは、6チームの組み合わせを変えて何度も試す道具だからで、
往復させると試行錯誤に使えない。データ量は数百試合ぶんで、転送量は小さい。

## 検討

| 選択肢                                       | 却下の理由                                                                                                               |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 構造モデルだけを使う（推定を持たない）       | 人力の実測が無いので、SU点をチーム別に割り振れない。2026-09-10 に前提が消えた                                            |
| 統計的推定だけを使う（OPR をそのまま当てる） | 乗数と加点が混ざった合計に線形モデルを当てることになり、内訳を説明できない。クライムが乗数であることを無視した推定になる |
| サーバ側で推定を計算する                     | 組み合わせを変えて試す道具であり、往復させると試行錯誤に使えない                                                         |
| 推定値を出さず公式の数字だけを見せる         | 公式サイトを見れば済む話になり、このアプリの付加価値が消える                                                             |

## 影響

推定値は必ず「推定」と明示して表示する。
公式の実測、推定、ピットでの申告の3種を混ぜない。
これは `AGENTS.md` の Invariants に「最も破られやすい境界」として登録した。

推定に使う項目（`capacity` / `climb_zone` / `partner_climb`）は
管理者が無効化できないようにする。消せると推定が黙って壊れる。

`details` に各ロボットのクライム結果が無かった場合、乗数と SU点 を
分離できない。その場合は画面から乗数の行を落とし、
分離できていないことを明示する。

## 追記（2026-09-22）

推定が読む項目は、無効化に加えて**入力形式の変更も拒む**。

`capacity` は個数を数値として読む。自由文へ変えられると数値として取り出せず、
抑制ユニットへの貢献の推定が黙って壊れる。`climb_zone` と `partner_climb` は
選択肢の識別子を読むので、選択式から外れると同じことが起きる。決定当時は
無効化だけを禁じていたが、禁じた理由（消せると推定が黙って壊れる）は
入力形式にもそのまま当てはまる。

ラベル・英語の質問文・補足・選択肢のラベルは直してよい。推定が読むのは
役割キーと選択肢の識別子であって、表示の文字ではない。管理者が言い回しを
直せないと、聞き取りの現場で通じない質問文を直せなくなる。
